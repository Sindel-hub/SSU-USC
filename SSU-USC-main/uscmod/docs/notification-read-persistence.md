# Notification read persistence

Every page with the existing student notification bar uses `dashboard/js/notifications.js`: Dashboard, Bulletin Board, Events, Organizational Chart, Tracklist, Election and Complaint. Officer bells currently contain a placeholder, with no separate read/unread feed to migrate. This change does not introduce new officer/admin notification types or redesign notification panels.

Read IDs are stored per authenticated account under `notification_reads/{uid}/items/{sha256(notificationId)}`. Only the existing authenticated hosted API reads/writes this collection; clients remain denied by the existing catch-all Firestore rules. The API derives the owner from the verified token, never from a requested UID. Only read metadata (ID and timestamp) is saved, not notification contents. Each mark request is limited to 100 IDs, and history is fetched in bounded pages. No index or client rule change is required.

The existing `uscNotificationRead:{uid}` browser cache is retained and migrated by merging it with the account state. Individual clicks and Mark all read update locally immediately and queue account synchronization. New sessions, navigation and a fresh browser retrieve cloud read IDs. Parallel tabs merge IDs rather than replacing a whole cloud list. Canonical cache ordering avoids storage-event feedback loops. Lost connectivity and blocked local storage do not turn in-memory read notifications back into unread; pending cache marks retry on the next page, panel opening, focus or online event. Synchronization failure is shown in the notification panel. If a browser closes while offline and browser storage is also unavailable, unuploaded marks cannot be recovered; reconnect before leaving in that situation.

Newly published items remain unread. Complaint status/classification/feedback changes retain the existing versioned notification IDs, so a genuinely new complaint update is a new notification. A read mark for an older complaint update does not suppress new feedback. Document IDs from Firestore, rather than a payload ID field, identify source records consistently.

Verification uses synthetic accounts and the real hosted handlers: persistence across fresh storage; migration; account isolation; stale account response rejection; bounded large batches/pagination; parallel tabs; offline retries; individual notification clicks; Mark all read; reload; all seven notification modules. No production records or accounts are modified by these tests. Actual deployed account access still requires staging verification.

Release through the existing development/PR/Preview workflow after review. The compatible API and shared UI must be deployed together. This is a server-owned additive read-state collection; no account or existing content migration is required. Initial deployment cannot reconstruct read marks that were already erased from browser storage before this fix. Production backend/configuration changes require separate authorization under the repository workflow.
