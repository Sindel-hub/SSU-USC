# Bulletin attachments and review

The existing announcement workflow and officer permission checks remain authoritative. The Create Announcement form accepts survey URLs in its content; the dedicated survey field is removed. Existing `surveyId` records still render their original Take Survey links. The Needs Assessment service is unchanged.

Images are selected cumulatively, previewed and removable before saving. JPEG, PNG and WebP inputs remain limited to 5 MB each, rasterized proportionally to at most 1200 pixels, and limited to 400,000 encoded characters per stored image. There is no application image-count cap. Each image uploads separately through the authenticated management API, avoiding the request and Firestore document limits for an inline image array. Existing platform storage/request/transaction quotas still apply.

New `announcement_images` documents are private under the existing default-deny Firestore rules. Uploads require draft permission. Draft attachment references are checked against their author's ownership; private image reads require authorized draft/review/publish access and membership in that draft. Image identifiers are immutable. Published records expose ordered image URLs through the existing announcement-image API, which verifies current publication and membership. Legacy single-image records continue to work. Removed or cancelled selections are never attached to a published post; unreferenced private uploads are retained, not exposed publicly.

The shared gallery renders one, two, three, or four visible images; additional images are available through the +N tile and the full-screen viewer. Keyboard arrows, previous/next buttons, mobile swipes, Escape and the close button navigate or dismiss the viewer. Full-size viewing uses object-fit: contain. The gallery is connected to the officer bulletin, officer overview, student dashboard/bulletin and public landing page. Content links are constructed from text nodes, limited to HTTP(S), with opener protection. They do not interpret HTML from announcements.

Review Announcements opens an independent scrolling dialog. Its badge comes from all authorized database records, independent of list pagination: submitted posts reviewable by the officer plus Ready posts they can publish. Own submissions count only when existing self-approval permission permits review. Drafts and revision requests remain editable in the dialog but do not inflate the pending counter. Local actions update the badge immediately; other users' changes refresh automatically every 15 seconds while the page is visible, and when the dialog opens or the tab becomes visible. Opening the dialog never marks a record processed.

Facebook cross-posting includes every attached image in one Page post. Multiple images upload as unpublished photos first, then the final feed post attaches their IDs in order. The existing private delivery image snapshot stores either the legacy single URL or a JSON array of URLs; no database migration is required. Failed unpublished uploads can retry without publishing a partial announcement. An ambiguous final publication remains uncertain and is not automatically resent. Single-image and text-only posts keep their existing paths. Meta may enforce its own API limits; images are never silently truncated. Already-successful deliveries are not reposted.

Deploy frontend and Node API changes together through the reviewed Vercel PR workflow. No rules migration, production record rewrite, or manual data conversion is needed. The Facebook multi-image fix additionally requires deployment of the updated Supabase `usc-facebook` Edge Function and its `media.mjs` dependency. Merging frontend code alone does not deploy this function. An authorized operator can deploy it with `supabase functions deploy usc-facebook --project-ref <reviewed-project-ref>` after approval of the target environment; existing secrets and access checks must remain configured. Live Facebook delivery, production Firebase access and a Vercel deployment were not performed during local validation.

Validation: `npm test`; `node tests/browser/announcement-review.cjs`. The browser test uses isolated Auth/Firestore doubles, actual HTTP handlers, image upload/serving and synthetic images. It covers cumulative selection/removal, review and publication, the badge, image grids/viewer, content links, legacy survey links and mobile layout. VM-based carousel/media/formatting test fixtures include the new renderer dependency without changing their assertions.

Facebook-specific validation: `node --test tests/facebook-publishing.test.mjs`. The harness executes the actual Edge handler with synthetic Firebase/Supabase records and a stub Graph API, covering multi-image ordering, partial upload failure, final-post uncertainty, URL validation, legacy snapshots and duplicate prevention. It does not send a live Facebook post.

## Legacy retry snapshot correction

The multi-photo publisher was already merged, but the atomic delivery reservation intentionally keeps its original `message` and `image_url` on retries. A confirmed failed delivery created by the old single-photo handler therefore returned only its first URL, even when the published announcement had a full `imageUrls` array. The regression test reproduced one photo request instead of four unpublished uploads plus one feed request.

The Edge Function now recognizes that precise legacy case (same message, first URL matches the published gallery), reserves the delivery using the existing RPC, and conditionally upgrades its private image snapshot before contacting Facebook. The update checks announcement, Page, sending state and attempt number. Successful and uncertain deliveries are not upgraded or resent. Missing or repeated photo IDs stop the operation before a partial public post can be published.

Deployment verification matters: GitHub/Vercel deployment alone does not deploy `usc-facebook`. The authenticated status response from the updated Edge Function includes `mediaVersion: ordered-gallery-v2`. Check that response after an authorized Supabase deployment to verify the running handler, without displaying tokens. The current live Edge Function version could not be inspected from this workspace; stale deployment remains a possible additional cause of first-image-only posts. No live Facebook test or production deployment was performed.

Tests cover no images, one, two, four and seven images; original order and complete title/body/links; disabled cross-posting; unpublished announcements; failed image uploads; concurrent clicks; retry snapshots; uncertain final publications; and missing/duplicate photo IDs. The Graph API and storage are isolated test doubles. Previously successful Facebook posts are not automatically edited or reposted by this fix.
